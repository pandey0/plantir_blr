# Implementation Notes

> **Ownership rule**: hit a gotcha, invariant, or edge case that isn't obvious from reading the code once → add it here in the same change. This is the "don't make the next person re-derive this" file — distinct from [`TECH_STACK.md`](TECH_STACK.md) (what we chose and why) and module `README.md`s (what a specific module does). If in doubt whether something belongs here or in a module doc: cross-cutting concerns spanning multiple call sites go here; single-module behavior goes in that module's doc with a pointer added here.

## Concurrency

- **Every state-transition write must be compare-and-swap, not read-then-write.** `events.updateStatus()` does `findUnique` (to validate the transition) then `updateMany({ where: { id, status: current.status } })` (to write only if nothing changed underneath us), not a plain `update`. Two concurrent callers reading the same "current" status and both passing validation is a real scenario (two authority users, a double-click, a retried request) — a plain `update` would let the second silently clobber the first with no error. If you add a new mutation with a "read current state, validate, write" shape, use this pattern, not `findUnique` + `update`.
- `updateMany`'s `count === 0` after a CAS write is ambiguous between "someone else already moved it" and "it genuinely doesn't allow this transition anymore" — we deliberately don't distinguish these to the caller (both surface as `InvalidStatusTransitionError`). Don't try to special-case the race — from the API consumer's side "you can't do that right now" is the correct signal either way.

## Enum boundary (Prisma ⟷ api-contracts)

- **Two independently-generated enum types share identical string values by deliberate design, but TypeScript string enums are nominal, not structural** — a bare value from one isn't assignable to the other without a boundary conversion, even though `EventCategory.POTHOLE === 'POTHOLE'` is true for both. `apps/intelligence-engine/src/events/prisma-enum.ts` (`toPrismaCategory`/`toPrismaStatus`) is the *only* place this conversion should happen. Don't add another cast site elsewhere — if you need the conversion somewhere new, import these functions.
- If `proto/plantir/events/v1/event.proto`'s `EventCategory`/`EventStatus` enum *values* (not just names) ever diverge from `packages/database/prisma/schema.prisma`'s, `prisma-enum.ts`'s indexing trick (`PrismaEnum[value as keyof typeof PrismaEnum]`) breaks silently at the type level (returns `undefined` at runtime for a mismatched key) — this is a real fragility to watch if either enum changes independently. There's no automated check tying them together today.

## Versioning

- **`/v1/` covers the real API contract only** — `GET /health` and `/dev/*` are deliberately outside it (infra/tooling, not contract). Don't move health checks or dev tooling under `/v1` "for consistency" — that's a category error, not a real inconsistency.
- No backward-compat aliases for the pre-`/v1` paths (`/report`, `/events`, etc.) — removed outright, not kept alongside. This was an explicit call: other apps (`public-map`) adjust to the engine when their turn comes, the engine doesn't carry compatibility shims for apps that haven't been touched yet. If you're the one updating `public-map` later: it currently calls the *old* unversioned paths and will need updating to `/v1/`, this is not an oversight.

## Confidence scoring

- **v2 landed 2026-08-10, reverses the v1 decision.** v1 (2026-08-09) was a flat additive formula chosen explicitly over `docs/product/VISION.md`'s multi-signal model. v2 implements that multi-signal model instead — user-confirmed reversal, see `TECH_STACK.md`'s decision log. Current formula (`events/index.ts`): reporter signal `min(60, 20 + 15*(reporters-1))` (diminishing returns, not unbounded `+20` per reporter), evidence signal `min(30, 15*evidenceCount)`, `+25` authority-confirmation bonus once status leaves `REPORTED`, `-50` FRAUD penalty, clamped `[0,100]`.
- **Weights are documented defaults, not calibrated** — there's no production traffic to tune them against yet. User explicitly deferred calibration to beta ("we can do it when the app goes to beta") — don't hand-tune these further pre-beta based on guesses; wait for real usage data.
- **Spatial/temporal signals are NOT separate additive terms.** VISION.md lists "reports within small radius" / "reports within short time window" as confidence signals — this repo expresses them as the *eligibility gate* for the reporter signal instead: a report only ever counts as an additional "unique reporter" if it passed duplicate/corroboration detection (below), which already requires spatial+temporal proximity. Don't add a second bonus for proximity on top of this — that would double-count the same signal.
- **A bare report with no `reporterId` scores 0**, not a hardcoded placeholder. `reporterId`/`mediaUrls` are both optional on `POST /v1/events` — an event created without either has nothing for the formula to count.
- **`trustWeight` is still accepted, still not used in the score** — same reasoning as v1: weighting by source trust needs a per-`Report` weight (schema change) and has zero observable effect while `citizen-report` is the only `Source`. Don't build it before a second weighted source exists.
- **`recalculateConfidence()` is now called on every `updateStatus()` transition, not just the FRAUD one** — v1 only recalculated on FRAUD because that was the only status the formula referenced; v2's authority-confirmation bonus means every transition can change the score (`REPORTED`→anything else gains `+25`).
- `Event.confidence_score`'s Prisma default is `0` — `createEvent()` relies on that default rather than setting a placeholder, then overwrites it via `recalculateConfidence()` once any linked `Report`/`Evidence` rows exist. Don't remove the `@default(0)` from the schema without checking this.

## Duplicate / corroboration detection (`createEvent()`, landed 2026-08-10)

- **Before creating a new `Event`, `createEvent()` checks for an existing non-terminal event of the same category within 150m and 6 hours** (`geo-query.ts`'s `findDuplicateCandidateEventId()`, constants `DUPLICATE_RADIUS_METERS`/`DUPLICATE_TIME_WINDOW_HOURS`) — if found, the new report attaches to it as a `Report`/`Evidence` instead of creating a second `Event` for the same real-world issue. This is what makes the reporter signal's "multiple reporters" case actually reachable via the real API for the first time (previously only exercisable by inserting `Report` rows directly in tests — see the now-superseded note that used to be here).
- **The time window is anchored to the candidate event's `created_at`, not sliding on each new corroborating report** — an event's corroboration eligibility window is bounded (6h from first report), not perpetually extended. A 7th report 6.5 hours after the first creates a new Event even if 5 reports corroborated in between.
- **Eligible statuses**: `REPORTED`, `VERIFIED`, `ESCALATED`, `IN_PROGRESS` — mirrors `ALLOWED_TRANSITIONS`' non-terminal states. `RESOLVED`/`FRAUD` events never receive new corroborating reports; a report matching one creates a fresh Event instead.
- **Picks the OLDEST matching candidate** (`ORDER BY created_at ASC LIMIT 1`) so confidence accumulates on one canonical event rather than fragmenting across near-simultaneous creates.
- **Runs inside `createEvent()`'s `$transaction`**, via a `db: Db` parameter (not the module-level `prisma`) so the duplicate lookup sees writes from the same transaction — required for correctness (see `db.ts`'s `Db` type, shared by `events/index.ts` and `events/geo-query.ts`).
- **Known residual race, not solved**: two fully concurrent `createEvent()` calls for the same real-world issue can still both miss each other and create two separate Events. Postgres's default READ COMMITTED isolation means each transaction only sees rows committed *before* it started — if both transactions start before either commits, neither sees the other's not-yet-committed row. Closing this needs row-level or advisory locking (e.g. lock on a category+grid-cell key), which is real added complexity not justified at this app's current traffic. If duplicate events start showing up under real concurrent load, this is the place to revisit.
- **A merge broadcasts `EVENT_UPDATED`, not `NEW_EVENT`** — a corroborating report doesn't create a new map marker, it changes an existing event's confidence (and implicitly its reporter/evidence counts). Only a genuine new `Event` broadcasts `NEW_EVENT`. `createEvent()`'s return value is identical either way (`Event` + `confidence_score`) — callers can't currently tell from the response alone whether their report merged or created; `POST /v1/events`'s response is `{ success: true, event_id }`, and a repeated `event_id` across two calls is the only current signal of a merge.

## GPS validation (`createEventRequestSchema`, landed 2026-08-10)

- `POST /v1/events` rejects coordinates outside a generous Bangalore-metro bounding box (`lat 12.7–13.2`, `lng 77.35–77.85`) with 400 `VALIDATION_ERROR` — `packages/api-contracts/src/schemas.ts`. Deliberately wide: a false rejection (blocking a real citizen report near the city's edge) is worse than a false acceptance (letting through a slightly-implausible-but-real report), so this catches only obviously-wrong coordinates (GPS spoofing, test data, a client bug sending `0,0`), not edge-of-metro legitimate reports.
- This is a schema-level check in `packages/api-contracts` (shared package), not engine-only — any future consumer of `createEventRequestSchema` (e.g. `citizen-app` validating client-side before submit) gets the same bounds for free.
- `POST /dev/inject` bypasses this schema entirely (calls `createEvent()` directly, not through `ingestEvent()`/the Zod schema) — its own `BLR_BOUNDS` constant in `app.ts` is unrelated and tighter, purely for generating realistic-looking synthetic demo data, not a validation boundary.

## Ward-based filtering (`GET /v1/events?wardId=`, landed 2026-08-10)

- Resolves the "no decision yet on whether the engine imports ward geometry into PostGIS or accepts it from the caller" question that used to be open here: **neither** — `apps/intelligence-engine/src/wards/` keeps its own copy of `bbmp-wards.json` (copied from `public-map/public/`, not imported across the app boundary — see `wards/README.md`), loaded into memory at startup, and the specific ward's geometry is passed as a query-time parameter into `ST_GeomFromGeoJSON()` (`geo-query.ts`'s `findEventIdsInWard()`). No new `Ward` table, no seed migration.
- **Only 225 of Bangalore's 243 BBMP wards have digitized boundaries** in the source GeoJSON — an unknown/undigitized `wardId` returns an empty event list (200, not 404/400), since it isn't a caller error, the data just doesn't cover that ward.
- Two copies of the same ward GeoJSON now exist in the repo (`apps/public-map/public/bbmp-wards.json`, `apps/intelligence-engine/src/wards/bbmp-wards.json`) with no enforced sync — a correction to one won't propagate to the other automatically. Accepted cost of keeping apps independently deployable (see root `CLAUDE.md`).
- Built via `npm run build`'s `tsc && cp` step (`apps/intelligence-engine/package.json`) — the JSON data file isn't a `.ts` source file `tsc` would otherwise copy into `dist/`, so the build script copies it explicitly. If you add another static data file under `src/`, check whether it needs the same treatment.

## Error handling conventions

- Domain errors are typed classes (`EventNotFoundError`, `InvalidStatusTransitionError` in `events/index.ts`), not generic `Error` or string-keyed objects — route handlers `instanceof`-check them to pick the HTTP status. If you add a new domain error, follow this pattern rather than throwing a plain `Error` and string-matching the message in the route handler.
- `ingestion.Source.normalize()` throws Zod's `ZodError` directly (not a wrapped domain error) — callers `instanceof z.ZodError` check. This is intentional: normalization failure *is* a validation failure, wrapping it would just be ceremony.
- **All error responses use `{ error: { code, message, details? } }`** (`errors.ts`'s `sendError()`), per `docs/standards/backend-engineering-standards.md` Section 13 — landed 2026-08-09, was previously an inconsistent mix of bare strings and raw Zod `flatten()` objects. `details` only appears for validation errors (400s) and only ever echoes the caller's own bad input back, never internal state.
- **`fastify.setErrorHandler` is a safety net, not the primary error-handling path** — most routes still explicitly catch known errors (`EventNotFoundError`, `ZodError`, etc.) and call `sendError()` themselves, because they need to pick a *specific* status code and error `code` per error type. The global handler exists for the remainder: anything ≥500 gets logged in full server-side (`fastify.log.error(error)`) and replaced with a generic `INTERNAL_ERROR` message to the client — never leak a raw exception message or stack trace. Known 4xx from trusted plugins (`@fastify/jwt`, `@fastify/rate-limit`) pass their own `.message` through, since that message is plugin-authored, not internal application state.

## Grid clustering (`GET /v1/events/clusters`)

- **Grid size is a step function over VISION.md's 4 documented zoom/grid-size points, not an interpolation.** The doc gives reference points (zoom 5→1km, 10→300m, 14→80m, 17→individual), not a formula — inventing a curve between them would be a design decision nobody made. `gridSizeMeters()` in `events/geo-query.ts` reproduces exactly those 4 points as range boundaries.
- **Meter→degree conversion uses a fixed Bangalore reference latitude (~13°N), not per-bbox recalculation.** A degree of longitude is `~111.32km * cos(latitude)` — this varies by latitude, so grid cells are only close-to-square near the reference latitude. Fine for a single-city app; would need fixing (compute from the query's own bbox center, not a hardcoded constant) if this ever serves a wider area. Don't assume it's geodetically correct elsewhere.
- **Test data hygiene matters more here than elsewhere**: clustering counts are sensitive to *any* stray row in the query's bbox, not just rows a test itself created. See `docs/architecture/TESTING.md`'s note on the 49-orphaned-row incident this surfaced.

## Environment / configuration

- **`DATABASE_URL` is never in `process.env` via any mechanism our own code controls.** Prisma's generated client (`node_modules/.prisma/client/index.js`) has a `schemaEnvPath` baked in at `prisma generate` time pointing at `packages/database/.env`, and loads it internally, lazily, the first time `new PrismaClient()` runs. A `node -e "console.log(process.env.DATABASE_URL)"` in this repo prints `undefined` even though the app connects to Postgres fine. **Do not add `DATABASE_URL` to `config.ts`'s env schema** — validating it there would either fail before Prisma's own lazy-load has run (if `config.ts` imports before `db.ts` does) or just duplicate Prisma's own env-sourcing for no benefit. `config.ts` is deliberately scoped to only the vars our own code reads directly (`NODE_ENV`, `JWT_SECRET`, `CORS_ORIGINS`).
- `config.ts`'s `buildConfig()` is pure (no I/O, no `process.exit`) specifically so it's unit-testable; the actual fail-fast behavior (`console.error` + `process.exit(1)` on invalid config) lives in the untested-by-design `loadConfig()` wrapper around it. If you add a new required env var, extend `buildConfig`'s logic, not `loadConfig`'s.

## Graceful shutdown

- `index.ts` handles `SIGTERM`/`SIGINT`: `fastify.close()` (stop accepting new connections, let in-flight requests finish) then `prisma.$disconnect()`, then `process.exit(0)`. Verified manually (not automated-tested — signal handling isn't practical to assert on in vitest): started the dev server directly with `node` (not through `nodemon`), sent a real `SIGTERM`, confirmed the `"shutting down gracefully"` log line appeared, port 3001 was freed, and the process exited.
- **`nodemon` logs `"app crashed"` for ANY child exit it didn't itself initiate, including a clean `process.exit(0)`** — it can't distinguish "child shut down gracefully because something else sent it SIGTERM" from an actual crash. Don't trust that message when testing shutdown behavior through `npm run dev:engine` (which runs under `nodemon`); test against a directly-spawned `node` process instead, or check the actual evidence (log line, port state, process state) rather than nodemon's summary.
- **Log output can be lost if `process.exit()` runs before stdout finishes flushing**, when stdout is redirected to a file/pipe (not a TTY) — Node's stdout write becomes asynchronous in that case, and an immediate `process.exit()` can cut it off before the buffer flushes. Hit this directly while verifying shutdown: the same code produced no visible log line on one run and the expected line on another, purely due to this race, not a logic difference. Don't conclude a handler didn't run just because its log line didn't appear when output is piped to a file — check for corroborating evidence (process/port state) too.

## Security headers

- `@fastify/helmet` registered with defaults (CSP, `X-Content-Type-Options`, `X-Frame-Options`, `Strict-Transport-Security`, etc.) — verified via `curl -D -` against a running instance, not just "should work because the plugin is registered." Defaults are appropriate for a pure JSON/WS API (this app serves no HTML) — no CSP tuning done or currently needed.

## Data model

- **`Event` → `Report`/`Evidence` has no cascade delete** (`packages/database/prisma/schema.prisma` — the relations aren't declared `onDelete: Cascade`). Deleting an `Event` that has linked `Report`/`Evidence` rows fails with a foreign-key violation. No app code deletes events today, so this hasn't mattered in production — it surfaced first in a test's cleanup (`afterEach` in `index.integration.test.ts`, which must delete `Report`/`Evidence` rows for an event before the event itself). If a delete-event feature is ever built, it needs to either cascade-delete children explicitly in a transaction or the schema needs `onDelete: Cascade` added (a migration) — don't assume `prisma.event.delete()` just works.

## Rate limiting

- **All route registration in `app.ts` happens inside `fastify.after(() => { ... })`, not synchronously right after the manifest loop starts.** This was a real bug, not a stylistic choice: `@fastify/rate-limit`'s per-route config (`config.rateLimit`) is picked up by an `onRoute` hook the plugin installs during its own registration, which — like all `fastify.register(...)` calls — completes asynchronously. Declaring routes synchronously immediately after `fastify.register(rateLimit, ...)` races that hook: the route can get declared before the plugin has finished loading, so the hook never sees it — **and this fails silently**. No error, no warning, the rate limit config is just quietly ignored and every request succeeds. Caught only because a dedicated test asserted the 11th request actually got a 429 and it didn't. If you add another plugin whose behavior depends on per-route `config`, keep the route registration inside `fastify.after()`, don't move it back out because it "looks like it should just work" synchronously.
- `@fastify/rate-limit` is registered with `global: false` — routes opt in via a `rateLimit` entry in `routes/manifest.ts`, not by default. Currently only `POST /v1/events` (10/min) — reads and transit's mocked data don't need it.
- **Default keying is by client IP** (`request.ip`), which is fine for now but has a real limitation: behind a reverse proxy without `trustProxy` configured, every request can appear to come from the proxy's IP, making the limit effectively global rather than per-client. Not configured yet — revisit when this is actually deployed behind a proxy/load balancer, don't assume IP-based limiting works correctly in that topology without checking.
- **Testing gotcha**: `fastify.inject()` always presents as the same IP (`127.0.0.1`), so every `POST /v1/events` call *in the same test file, using the same `app` instance* shares one rate-limit bucket — not just the ones inside a test that's explicitly testing rate limiting. `index.integration.test.ts` has ~8 such calls across unrelated tests before the dedicated rate-limit test; that test spins up its own `buildApp()` instance specifically to get a clean counter rather than fighting the shared one. If you add more `POST /v1/events` calls to tests using the shared `app`, be aware you're spending down the same 10/min budget — the suite runs in well under a minute, so this is a real, not theoretical, way to get a flaky 429 that has nothing to do with the thing you're testing.

## Real-world edge cases already handled — don't re-break them

- Latitude/longitude range validation (`[-90,90]`/`[-180,180]`) happens in the Zod schema, not the DB — PostGIS would silently accept out-of-range values via `ST_MakePoint` without erroring in ways that map cleanly to a 400.
- JWT expiry (2h on dev-issued tokens) surfaces as a generic 401 via the existing `jwtVerify()` try/catch — no special-casing needed, don't add an "expired vs invalid" distinction unless a real product need shows up (it changes nothing about what the client should do: re-auth either way).
- `POST /dev/inject` and `POST /dev/token` are excluded from production **at route-registration time** (the route doesn't exist), not via a runtime `if (isProduction) return 403`. If you add a new dev-only route, register it the same way — a runtime check is one missed `if` away from being live in prod; non-registration can't be.

## Things explicitly deferred (not forgotten, don't silently build them)

- AI-based fraud detection / media verification (`docs/product/VISION.md`'s Fraud Prevention section) — requires a third-party AI vendor, which is a "major" change per `TECH_STACK.md`'s criteria. Don't wire up a real AI call without that conversation happening first.
- Camera-only uploads / user reputation scoring (same VISION.md section) — no upload pipeline and no user account system exist respectively; each is its own real feature, not an engine-only change.
- Real login/identity for citizen-app/authority-portal — `/dev/token` is explicitly a placeholder (see `docs/api/intelligence-engine.md`). Building real auth is itself a "major" change per `TECH_STACK.md`.
- `Idempotency-Key` support on `POST /v1/events` — a retried request (e.g. a flaky mobile connection) still isn't idempotent at the HTTP layer; duplicate/corroboration detection (above) reduces the practical impact for genuinely-duplicate *content* but doesn't make a literal retry of the same request safe from creating a second Report. Tracked in `docs/architecture/STANDARDS_COMPLIANCE.md` row #15, not fixed this round.
